# 流量切换网关（HTTP 服务平滑升级）

值班工程师升级 HTTP 服务时：用本网关把流量从旧副本平稳切到新副本，并明确知道
**什么时候可以安全停掉旧副本**。

- `gateway/`  FastAPI 网关：反向代理 + 切换状态机 + 在途请求恰好一次计数 + 操作网页
- `replica/`  FastAPI 业务副本（old/new 同一镜像）：可模拟慢响应与健康变化
- `tests/`    端到端自测（真实启动三进程，覆盖关键交错场景）
- `docker-compose.yml`  一键启动网关 + 两个副本

## 快速开始

```bash
docker compose up --build
# 打开 http://localhost:8000  （只有网关对外暴露端口）
```

网页上可以：发测试请求（含并发、慢请求、客户端中途断开）、发起切换、宣告完成、
手动回滚、模拟副本健康变化与慢响应，并实时查看每个请求的去向与状态、在途计数、
超时待确认请求与旧副本停机受阻明细、事件日志和“旧副本是否可停机”。

本地无 Docker 开发：

```bash
pip install -r gateway/requirements.txt
cd replica  && REPLICA_ID=old PORT=8001 uvicorn main:app --port 8001 &
cd replica  && REPLICA_ID=new PORT=8002 uvicorn main:app --port 8002 &
cd gateway  && OLD_URL=http://127.0.0.1:8001 NEW_URL=http://127.0.0.1:8002 \
              uvicorn main:app --port 8000
```

## 切换语义（状态机）

```
                 新副本健康检查通过
   old 接单  ───────────────────────►  new 接单（未宣告完成）
   （active=old）                        ▲   │  新副本失效（周期探测发现）
        ▲                                │   ▼
        └──────────  自动/手动回滚  ──────┘   宣告完成（要求 new 健康）
                                             │
                                             ▼
                                    new 接单（已宣告，回滚禁用）
                                    旧副本在途/待确认清零 => 可停机
```

- **新副本未就绪**：`POST /ops/switch` 前实时探活，不健康则拒绝（409），旧副本继续接单。
- **切换后**：新请求只进新副本；旧副本已受理的请求继续执行到真正结束（排水）。
- **可停机条件**：`已宣告完成 且 旧副本在途 == 0 且 无超时待确认请求`。
  未宣告完成时旧副本必须留着兜底（新副本随时可能失效需要回滚），所以光
  “在途为 0”还不够；网关超时的请求在副本确认处理结束前同样阻止停机。
- **宣告完成前新副本失效**：健康探测（`POLL_INTERVAL`，默认 1s）发现后自动回滚，
  旧副本重新接单；也可手动回滚。宣告完成后回滚禁用。
- **客户端超时/断连 ≠ 上游已结束**：网关处理器等待上游响应时用 `asyncio.shield`
  保护上游任务。客户端断开只会取消“等待”的处理器协程，上游请求继续执行，
  计数只在上游真正结束（响应到达/出错）时扣减。
- **网关 `UPSTREAM_TIMEOUT` ≠ 上游已结束（超时排水判断）**：等待上游超过
  `UPSTREAM_TIMEOUT` 时，客户端**及时收到 502**，但该请求不计完成也不计失败，
  而是转入 **待确认（unconfirmed）**，继续阻止旧副本停机。网关的核对器
  （`CONFIRM_POLL_INTERVAL`，默认 1s）向副本按请求 ID 核对真实结局：
  - 副本回报 `served` -> 原请求确已处理完成，转入完成计数并解除停机阻止；
  - 副本回报 `in-flight` -> 原请求仍在处理，继续阻止；
  - 副本暂不可查（进程宕机/网络不通）-> 保持未确认，下轮继续查；
  - 副本重启（进程启动标识 `boot_id` 变化）后查无原请求 -> 标记
    “副本重启未确认”，**新进程空闲绝不等于原请求已结束**，只能人工确认
    （`POST /ops/request/{id}/ack`）后才解除阻止；
  - 同进程查无记录且该进程已无在途请求（记录被有界淘汰）-> 可确认结束。

## 恰好一次计数（不重计、不漏计）

1. **受理恰好一次**：在 `asyncio.Lock` 内读取当前活动副本、`in_flight[active] += 1`
   并创建上游任务，中间没有任何 `await`——切换/回滚无法插入，每个请求必然且只
   会计入一个副本。
2. **完成恰好一次**：每个受理的请求对应恰好一个上游任务，其 `done_callback`
   恰好执行一次（在事件循环内同步执行，天然原子），且只在**上游真正结束**时触发。
3. 不变式任意时刻成立：`admitted == completed + failed + in_flight + unconfirmed`
   （按副本分别成立；`unconfirmed` 为网关已超时、等待副本核对结局的请求），
   状态接口返回锁内一致快照，自测在并发交错中持续采样校验该式。
4. 网关对上游不做重试，请求 ID 单调递增并随 `X-Request-Id` 下发，副本记录实收 ID
   与每个 ID 的处理状态（in-flight/served），可逐条核对“每个请求恰好送达一次”。
5. 超时请求的状态流转也是恰好一次：超时瞬间在 done 回调里 `in_flight -= 1`、
   `unconfirmed += 1`；核对确认后 `unconfirmed -= 1`、`completed += 1`
   （人工确认则计入 `failed` 并保留审计原因），不重计不漏计。

## API 一览

| 方法/路径 | 说明 |
| --- | --- |
| `GET /` | 操作网页 |
| `ANY /api/{path}` | 反向代理到当前活动副本 |
| `POST /ops/switch` | 发起切换（新副本未就绪则 409，旧副本继续接单） |
| `POST /ops/declare-complete` | 宣告完成（需已切换且新副本健康；之后禁用回滚） |
| `POST /ops/rollback` | 手动回滚（仅宣告完成前） |
| `POST /ops/reset` | 演示复位（需在途为 0；清空事件/请求日志，计数器保持累计） |
| `GET /ops/status` | 状态快照：活动副本、在途、待确认、健康、计数、停机受阻明细、事件、最近请求、`safe_to_stop_old` |
| `POST /ops/request/{id}/ack` | 人工确认一个待确认请求（副本重启等无法自动核对的场景），确认后解除停机阻止 |
| `POST /ops/replica/{old,new}/health?healthy=` | 模拟副本健康变化 |
| `POST /ops/replica/{old,new}/delay?delay_ms=` | 模拟副本慢响应 |
| `GET /ops/replica/{old,new}/state` | 副本自身观测（在途/实收/已服务/请求ID/进程启动标识） |

副本直连接口（容器网络内）：`GET /api/work?delay_ms=`、`GET /healthz`、
`POST /control/health`、`POST /control/delay`、`GET /control/boot-id`、
`GET /control/requests?ids=1,2,3`（按请求 ID 批量回报 in-flight/served/unknown）、
`GET /state`。

## 自测

```bash
python3 tests/run_e2e.py     # 自动启动 网关+两副本，跑完自动清理
```

覆盖场景（最近一次运行 13/13 通过）：

- S1 初始路由到旧副本；操作网页可访问
- S2 新副本未就绪拒绝切换、旧副本继续接单
- S3 就绪后切换、新请求只进新副本
- S4 旧副本慢请求在途时切换+宣告完成，**在途真正清零前不显示可停机**
- S5 宣告完成前新副本失效 → 自动回滚、旧副本重新接单
- S6 宣告完成后新副本失效不再回滚
- S7 客户端 0.5s 超时断开，上游慢请求：**在途保持为 1 直到上游真正结束**，
  副本侧也确认该请求真正执行完成
- S8 40 并发请求 × 新副本健康抖动 × 随机切换/回滚交错：全程采样计数不变式，
  结束后网关计数与两副本实收/已服务逐一对账，请求 ID 无重复无遗漏
- S9 宣告完成的门槛（未切换 409）与幂等
- S10 直接取消处理器协程（模拟服务器在客户端断连时取消应用协程的行为）：
  shield 保护的上游任务继续到真正结束才扣减计数，记录标记 `client_gone`
- S11 网关 `UPSTREAM_TIMEOUT`（测试内 2s）：客户端在约 2s 及时收到 502，
  旧副本仍在处理期间 `safe_to_stop_old=False`、网页可见受阻明细；副本处理完
  被核对器确认后自动解除并计入完成
- S12 待确认期间副本宕机（暂不可查）与重启（boot_id 变化、查无原请求）：
  全程保持未确认、新进程空闲不误判为原请求结束；人工确认后才结案，未知 ID 返回 404
- S13 超时请求与正常请求、切换/回滚交错：超时请求始终挂在实际受理的 old 上，
  计数不变式全程成立，结束后网关与两副本实收/完成逐一对账

## 已知限制

- 单进程内存状态：网关重启后计数与切换状态丢失（演示场景可接受）。
- 健康判定只有 `/healthz` 二元结果；未做被动健康（按上游 5xx 比例摘流）。
- 自动回滚的感知时延取决于 `POLL_INTERVAL`。
- 网关调上游有 `UPSTREAM_TIMEOUT`（默认 120s）兜底：超时后客户端立即收到 502，
  但请求转入“待确认”继续阻止停机，由核对器向副本确认真实结局（详见上文
  “网关 UPSTREAM_TIMEOUT ≠ 上游已结束”），不再像普通失败那样立即扣减在途。
- 副本“失效”是健康检查返回 503；进程级宕机（`docker compose stop old-replica`）
  同样会被探活判为失效。副本宕机期间待确认请求保持未确认；副本重启后 boot_id
  变化，原请求无法自动核对，需在网页或 `POST /ops/request/{id}/ack` 人工确认。
- 待确认/请求记录为单进程内存状态：网关重启后这些状态丢失（演示场景可接受）；
  副本侧请求状态为有界保留（默认 5000 条），超出淘汰最旧记录。
